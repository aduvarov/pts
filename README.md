## 13.2. Bridge

#### Вступление: Проблема комбинаторики классов

-   Сценарий: Создание приложения для отправки уведомлений через разные платформы (Telegram, WhatsApp) и с различными типами уведомлений (мгновенные, отложенные).
-   Проблема: Рост количества классов с добавлением каждого нового провайдера и типа уведомлений.

#### Описание паттерна Мост

-   **Цель:** Избежать экспоненциальный рост количества классов.
-   **Ключевая идея:** Разделение абстракции (типа уведомлений) и реализации (провайдеров уведомлений), используя композицию вместо наследования.

#### Пример реализации

1.  **Создание интерфейса** `Provider`:
    -   Определяет методы для отправки сообщений, подключения и отключения.
2.  **Реализация провайдеров**:
    -   Создание классов для различных провайдеров (например, `TelegramProvider` и `WhatsAppProvider`), реализующих интерфейс `Provider`.
3.  **Создание управляющего класса** `NotificationSender`:
    -   Принимает объект `Provider` через конструктор.
    -   Имеет методы для отправки уведомлений при помощи провайдера.
4.  **Преимущества паттерна Мост**:
    -   Упрощение расширения функционала (добавление новых типов уведомлений или новых провайдеров не требует создания дополнительных классов).
    -   Снижение сложности за счет избегания множественного наследования.
